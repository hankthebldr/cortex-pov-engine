Read-only audit of the FY27 v2.2 Use-Case / Test-Case index as it is bound to
this engine, run ahead of the XSIAM tenant wiring. Every number below was
counted on the tree at `46623d8` (main), not quoted from a doc. Where a doc
disagrees with the count, the count wins and the doc is listed in §1.

--check` **in sync**, crosswalk **177 rows / 0 unresolved**, snapshot tabs
internally consistent (266 ids identical across `tc_index` and
`detection_spec`, 0 duplicate ids, 0 dangling `uc_id`, 0 dangling
`pov_scenario_id`).

The engine side is clean. The two things this audit surfaces are (a) the
in-tree "current state" documents disagree with each other and with the tree,
including the generated scoreboard, and (b) the tenant read-back path as built

defects that would turn a shared, busy tenant into inflated or truncated
coverage. §4 is the wiring backlog in priority order.

## 2 · Index content — what the snapshot itself says

**Internally consistent, externally stale.** The eight tabs agree with each
other. What they do not reflect is anything the engine has done since
2026-07-31:

- `content_status` is **`TO AUTHOR` on all 107** DET/HNT rows, although 70
  are evidenced. The engine feeds `engine_coverage_v2.3.csv` back, but the
  detection-spec tab never consumes it. Two sources of truth for "is this
  authored" now exist and only one moves.
- `pre_req_setup` is the literal placeholder `TBD — confirm tenant state…`
  on **all 266** rows, and `tool_script_ref` points every row at a
  `pov-scripts/…` path that exists in no repo this engine knows about.
- **23 rows are `Draft`**: all of `UC-AEPS` (3), `UC-APB` (10), `UC-XTI`
  (10). Three assertion artifacts and one scenario already bind Draft rows
  (`TC-AEPS-01/02`, `TC-APB-02/05`, `TC-XTI-01`). Evidence against a Draft
  row is evidence against a moving target; the index owner should either
  promote them or the crosswalk should flag the binding.
- The **16 proposed v2.3 rows** (`UC-AIACC` 5, `UC-BROWSER` 6, `UC-AEPS` 5)
  are still unmerged. Consequence below.

**Evidence is concentrated, not spread.** 372 bindings across 90 rows; the

## 3 · What the tenant loop can actually prove — the measurability ceiling

The XSIAM read-back path (`core/connectors/`) produces exactly one measured
quantity: **MTTD** per seeded `Result`, from `observed_at − executed_at`.
`verifier.score_run` scores a run against its scenario threshold only when
`primary_kpi` is MTTD-shaped, or when a caller supplies `measured_value`,
which no production caller does.

Walking that constraint through the bindings:

| filter | scenarios | DET/HNT rows |
|---|---:|---:|
| bound at all | 177 | 70 |
| … whose index row carries a numeric threshold | — | 30 |
| … reachable by an MTTD-shaped scenario (59 of 177) | 59 | 28 |
| … **both** (machine `pass` is possible today) | — | **6** |

The six: `TC-AGTX-07`, `TC-AGTX-11`, `TC-AIRS-07`, `TC-DLP-01`, `TC-DLP-05`,
`TC-DLP-11`. Everything else the loop touches resolves `not_applicable`
(qualitative row, 40 of the 70) or `pending` forever (numeric row, but the
scenario's KPI is one the engine never measures).

Where the other 118 scenarios' KPIs go:

| scenario `primary_kpi` | scenarios | needs from the tenant |
|---|---:|---|
| MTTD | 59 | `get_alerts` — **wired** |
| Detection Accuracy | 50 | observed ÷ seeded per run — the reconcile loop already computes both halves (`efficacy_summary`) and throws the ratio away |
| Cross-Source Correlation Rate / Stitch / Causality | 33 | `get_incidents` — did N alerts collapse into 1 incident — **not wired**; the connector reads alerts only |
| Asset/Compliance/Coverage/other | 29 | XQL over posture datasets — Tier-2 `xsiam_tenant` path, assertion-shaped |
| none | 6 | — |

The single highest-leverage change for the wiring sprint is therefore not a
new endpoint: it is passing `matched / seeded` from `apply_verdicts` into
`score_run` as `measured_value` for Detection-Accuracy scenarios. That alone
lifts the machine-PASS-reachable set from 6 rows to **14** (adds `TC-AES-01/
05/06/07`, `TC-AIRS-01/08`, `TC-XTI-05/07`) with zero extra tenant calls.
`get_incidents` for the correlation KPIs is the second lever: 18 scoreable
DET/HNT rows sit behind it, including all five `UC-IR` rows on the
`incidents` dataset.

## 4 · Read-back path review — defects to fix before pointing it at a tenant

Reviewed: `core/connectors/xsiam.py`, `matcher.py`, `service.py`,
`preflight.py`, the seeding in `engine/orchestrator.py`, against the repo's
own API reference (`docs/reference/xsiam-platform-apis/04-alerts-api.md`) and
the Phase 9 design (`docs/superpowers/specs/2026-05-15-…`). PANW's live API
docs were not reachable from this session (egress-blocked), so items marked
*verify* need one call against the tenant, which item 1 turns into a
preflight stage.

1. **No pagination, truncation invisible.** `_build_request` asks for one
   page (`search_to: 100`, sorted `creation_time asc`) over
   `[min(executed_at), now+5m]` with no host filter. A customer tenant that
   raises more than 100 alerts in that window — tenant-wide, any host —
   silently drops the newest ones, which on an ascending sort are the run's
   own. `reply.total_count` / `result_count` are never read, so the summary
   cannot say "floor, not measurement" the way it already does for dropped
   timestamps. The Phase 9 design specified paging by narrowing time
   filters; it was not built. *Fix:* loop `search_from/search_to` or split
   the window, and mark the summary degraded when `total_count > returned`.

2. **No host or identity scoping.** `ObservedAlert.host` is captured and
   never used; `Run.target` / the agent's hostname is never passed to the
   matcher. Combined with the `technique-base` key (a `T1003` step matches
   any `T1003.*` alert from any endpoint), a shared or noisy tenant yields
   MTTD for detections that fired on someone else's host. This is the
   Option-A "where it breaks down" case from the Phase 9 doc, and it is the
   default. *Fix:* `alert_source`/host filter in the request where the run
   has a known target, and a `host` key in `_keys_for` that is required
   when both sides carry one.

3. **The `detection_id` key is dead on XSIAM.** `_normalize_alert` reads
   `detector_id | bioc_id | rule_id`; none appears in the documented alert
   object (the reference shows `name`, `source`, `category`,
   `mitre_technique_id_and_name`, …). Seeded `Result.detection_id` is a
   card-local slug (`bioc-edr-001-shadow-file-read-…`) that could never equal
   a tenant rule id anyway. Matching therefore rests on technique or a
   two-token name overlap. *Verify* which rule-identifying field the tenant
   returns (`matching_service_rule_id` is the likely one), then decide
   whether cards should carry the tenant rule name as a match key.

4. **One alert satisfies every detection in a step.** The orchestrator seeds
   `Result.mitre_technique` from the *step's* technique, so all N expected
   detections of a step share it; the matcher never consumes an alert, so a
   single alert marks all N observed with the same MTTD. A step expecting
   BIOC + XQL + Correlation reads as 3/3 on one BIOC firing. *Fix:* capture
   the alert's `source` / `alert_type` into `ObservedAlert` and require it to
   agree with `Result.signal_type` (BIOC ↔ "XDR BIOC", Analytics ↔ "XDR
   Analytics BIOC", Correlation ↔ "Correlation", IOC ↔ "XDR IOC") — this is
   also what lets the UC/TC surface report proof per `detection_type`.

5. **Endpoint version.** The connector calls
   `/public_api/v1/alerts/get_alerts_multi_events`; the vendor's current
   reference lists v1 as legacy in favour of a v2 path with a different
   envelope. *Verify* on the tenant and make the path a config field rather
   than a class constant, so a tenant on the new API is a setting, not a
   patch.

6. **Multi-technique strings.** `_technique_id` uses `re.search`, so a
   value like `"T1059.001, T1003.008 - …"` yields only the first id.
   `findall` is the one-line fix.

7. **Two credentials, one tenant.** Reconcile pulls under kind `xsiam`,
   Tier-2 XQL under `xsiam_tenant`, deliberately. The connector already
   accepts `base_url`, so one `xsiam_tenant` registration can serve both,
   but nothing in the console or `.env.example` says so. The wiring runbook
   should register one credential and state which paths it authorises.

What is already right and should not be touched: application errors inside a
200 raise instead of reading as zero alerts; an unreadable timestamp drops
the alert and says so; every no-tenant / 401 / 429 / bad-dataset path resolves
`pending`, never `fail`; auto-reconcile is off by default and budgeted when
on; the preflight ladder reports every rung and carries `queries_issued`.

## 5 · Recommended order for the wiring sprint

1. **Preflight alert-shape probe** (extends `preflight_reconcile`): pull one
   alert, report which of the keys the connector reads are present, which
   `source` values the tenant emits, and `total_count`. Closes the three
   *verify* items above in one call and makes "will matching work?" a rung.
2. Pagination + `total_count` degradation (item 1) and host scoping (item 2).
3. `source`-aware matching (item 4) and `findall` (item 6).
4. `measured_value = matched/seeded` for Detection-Accuracy scenarios — the
   6 → 14 lift in §3.
5. `get_incidents` read + a `CorrelationRate` measured value for the 33
   stitch scenarios.
6. Fix `--emit-xlsx` to walk `assertions/` rather than the hand-list, then
   regenerate the scoreboard, and refresh the coverage tables in `CLAUDE.md`,
   `README.md`, `index-gaps-v2.2.md` from `ground-truth.md`.
7. Widen `_evidence_index` to the two fields already specified in
   `CLAUDE.md` — `authored` and `proven` — so the first tenant run moves a
   number that today cannot move.

Items 1–3 are prerequisites for trusting any number the loop produces; 4–5
decide how many index rows a tenant run can ever turn green; 6–7 are the
honesty debt this audit found. None of 1–7 adds a write path to Cortex.

## Method

Counts: `python3 scripts/uctc_crosswalk_v2.2.py --report`, `--emit-xlsx
--check`, `pytest tests/engine/test_corpus_refs_strict.py`, plus direct
`pyyaml` walks of `scenarios/**` and `assertions/**` joined to
`_v2.2-source/detection_spec_v2.2.csv`. "Numeric threshold" means the index
`threshold` contains a digit and is not `Qualitative pass`; it matches the
registry's `is_scoreable` on 91 rows. "MTTD-shaped" matches
`verifier._is_mttd`. No tenant was contacted; *tenant-verified* remains 0.
