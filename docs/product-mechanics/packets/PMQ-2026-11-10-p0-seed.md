### PM-ING-01 — P0 — Ingestion, parsing and XDM modeling

**Question.** When the HTTP log collector (cloud /logs/v1/event or Broker VM HTTP applet) returns 2xx, is the record guaranteed to be parsed into its dataset, or can it be accepted and then dropped by the parsing rule (bad JSON, missing or unparseable timestamp, oversize field)? Where does a dropped record become visible (an error dataset, a collector health metric, nowhere)?

**Why we ask.** delivery.py counts 2xx as delivered. If accepted is not the same as parsed, every "delivered" campaign verdict can hide an empty dataset.

**What the answer changes.** Add a post-delivery canary row-count probe before a step may claim `delivered`; add a parse-failure code to the delivery taxonomy.
- *if* 2xx guarantees parse → Keep the delivery verdict; document it as proven.
- *if* accepted can still be dropped → Split `accepted` from `landed` in the verdict; landed requires an XQL hit on the canary.

**Could be settled in the lab.** POST one well-formed and one malformed record carrying distinct canaries to a lab collector; query both canaries after 10 minutes.

**Background — our current working model of ING.** Everything between "the emitter POSTed a record" and "a detector can read it": the HTTP log collector (cloud /logs/v1/event or the Broker VM HTTP applet), dataset routing, the parsing rule, the `_time` the record is filed under, and the XDM modeling rule that maps raw fields onto the common schema. A record that is accepted but never lands, or lands under the wrong time or dataset, is a silent false negative at every layer above it.
